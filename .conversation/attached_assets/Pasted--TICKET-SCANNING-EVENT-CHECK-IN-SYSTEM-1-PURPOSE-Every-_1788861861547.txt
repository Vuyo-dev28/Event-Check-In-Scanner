# TICKET SCANNING & EVENT CHECK-IN SYSTEM

## 1. PURPOSE

Every event business must be able to scan and validate tickets sold through the platform.

The system must allow event organizers to use a smartphone, tablet, or computer with a camera to scan customer QR codes at the event entrance.

The scanning experience must be extremely fast and simple.

The ideal workflow is:

Customer arrives

↓

Shows digital ticket

↓

Staff opens Check-In Scanner

↓

Camera scans QR code

↓

System validates ticket

↓

Large result appears

↓

Staff allows or denies entry

↓

Ticket becomes CHECKED_IN

# 5. QR CODE CONTENT

Do not place sensitive customer information directly inside the QR code.

The QR code should contain a secure ticket token.

Example:

ticket_token

or a cryptographically secure ticket reference.

Never encode:

* Payment card information
* Passwords
* Full customer data
* Private API keys
* Sensitive financial information

---

↓

↓

The frontend must NEVER independently decide whether a ticket is valid.

# 28. DATABASE TRANSACTION SAFETY

This is critical.

Two scanners could theoretically scan the same ticket at exactly the same time.

Example:

Scanner A scans ticket.

Scanner B scans same ticket.

Both requests arrive simultaneously.

The backend must guarantee that only ONE scanner can successfully check in the ticket.

Use an atomic database operation/transaction.

Conceptually:

IF ticket.status = ACTIVE

THEN

set ticket.status = CHECKED_IN

ELSE

reject check-in

This must happen server-side.

Do NOT implement this logic only in the frontend.

---

# 29. DOUBLE-SCAN PROTECTION

Example:

Scanner A:

10:42:01

Ticket scanned.

Scanner B:

10:42:01

Same ticket scanned.

Only one request succeeds.

The other receives:

ALREADY_CHECKED_IN

This prevents duplicate entry.

# 30. OFFLINE CHECK-IN

Prepare the architecture for offline scanning.

Eventually support:

Online mode

Offline mode

When offline:

The scanner can use an encrypted/local event ticket dataset.

Scan tickets.

Queue check-ins locally.

When connection returns:

Synchronize check-ins.

Resolve conflicts.

IMPORTANT:

Do not implement insecure offline validation.

The backend remains the authoritative source.

# 51. SCREENSHOT CONSIDERATIONS

The system must NOT assume that screenshots are valid or invalid.

The QR token must be validated against backend ticket state.

If a customer screenshots a ticket before transferring/refunding it, the backend must still determine whether that token remains valid.

---

# 52. QR TOKEN ROTATION

Where appropriate, design the system so QR tokens can be rotated or invalidated.

When ticket is:

Transferred

Refunded

Cancelled

Revoked

the old token must no longer validate.

---

# 53. SECURITY

Never trust:

* Client-side ticket status
* Client-side event ID
* Client-side attendee ID
* Client-side check-in status

The backend must determine:

Who is scanning.

Which event they are assigned to.

Whether the ticket exists.

Whether the ticket belongs to that event.

Whether the ticket is paid.

Whether the ticket is refunded.

Whether the ticket was transferred.

Whether the ticket was already used.

Whether the staff member has permission.

# 61. FINAL REQUIREMENT

Ticket scanning is a CORE feature of the platform.

Do not treat it as a future placeholder.

The initial frontend must include a complete simulated scanning experience with:

* Camera scanner interface
* QR code detection architecture
* Manual ticket lookup
* Ticket validation
* Valid ticket
* Invalid ticket
* Already checked-in ticket
* Refunded ticket
* Cancelled ticket
* Transferred ticket
* Wrong event
* Expired ticket
* Check-in confirmation
* Multiple scanners
* Scanner sessions
* Staff permissions
* Entrance management
* Live check-in statistics
* Check-in history
* Check-in analytics
* Audit logging
* Mobile-first UI
* Continuous scanning
* Offline-ready architecture

The system must be designed so the mock scanner can later be connected to Supabase without changing the scanner UI.
